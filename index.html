Layer 2 — Colour schemes

Schemes

Colour carries no fixed meaning in this system — meaning is deferred to context. A scheme is one slot recipe applied to a family: the same eight slots, derived the same way, whichever family fills them.

The slot contract

Components only ever read the slots — --surface-bg, --surface-bg-1, --text-fg-1, --text-fg-2, --surface-border, --action-bg-1, --action-fg-1, --action-border — never a family colour directly. For any family F:

--action-border is the border of the secondary (outline) action — the button with a transparent background and its label in --text-fg-1. It mirrors the action-bg-1 step in every scheme, so the secondary outline always tracks the primary action’s colour. Slot names follow Donnie D’Amato’s [purpose]-[property]-[priority] construction from Mise en Mode, in a shortened form: 1 always means primary, 2 always means secondary, and 3 is reserved for auxiliary if it is ever needed. The dark derivation leans on the 300-on-1000 pairing (≈6.6–8.3:1 across families) for secondary text, while actions on dark use the brighter F-200. Every light family uses F-700 for both action-bg-1 and action-border. On dark, all families use F-200 for both action-bg-1 and action-border.

Layer 1 — Primitives

Fluid type

Utopia scale: 360px → 18px base at a 1.125 ratio; 1240px → 20px base at 1.2. Twelve steps, named by percentage of the base — 100 is the base value, and every name is that step’s approximate size as a percentage of it (60, 70, 80, 100, 120, 140, 160, 180, 200, 250, 300, 350). The spacing scale below uses the same convention on the same base — its 100 is identical to this 100 — and the numbers share the colour ramps’ numeric vocabulary. Sizes shown are measured live from this page at your current window width. Note steps 60 and 70 have negative slopes — the two ratios cross below step 100, so they render about 1px smaller on desktop than on mobile. No step carries its own clamp(): one shared progress value — how far the viewport sits between 360px and 1240px, 0 to 1 — drives the whole scale, and each step is derived from the configuration above as base × ratiostep at both ends, interpolated by that progress. The progress is computed by the CSS progress() function where supported, the tan(atan2()) construction elsewhere, with the original per-step clamp() definitions kept as the floor for engines with neither.

Typography utilities

Ratified utility classes from typography.css — each role’s family, weight, leading, tracking and variation settings, with its size mapped onto the fluid scale above. Role names are spelled out — Heading, Paragraph, Action, and Detail (formerly Labels & Data). Leading variables: --leading-none 1, --leading-compact 1.25, --leading-relaxed 1.5. Tracking variables: --tracking-tight −0.03em, --tracking-none 0, --tracking-loose 0.05em, --tracking-extra-loose 0.1em. Families resolve through the brand-pack tokens in fonts.css — --font-main (IBM Plex Sans), --font-alt (Fraunces), --font-mono (IBM Plex Mono, assigned but not yet loaded) — so a different brand swaps typefaces here without touching the role classes; leading and tracking are brand-pack values too, since neither transfers consistently across typefaces.

Layer 1 — Primitives

Fluid spacing

Thirteen steps on the same Utopia configuration as the type scale, named by the same convention: 100 is the base value — and here it is literally the same value, --space-100 being identical to --step-100 — with every other name that step’s approximate percentage of base (10, 30, 50, 60, 70, 80, 100, 125, 150, 200, 300, 400, 500). One-up pairs are named <low>-<high>, e.g. --space-100-200. Bar widths and pixel values are measured live. No step or pair carries its own clamp(): the same shared progress value that drives the type scale drives this one, and each step is derived from the shared configuration as its multiplier of the base size at both ends — rounded to the whole pixel, which is what keeps --space-30 constant below — interpolated by that progress. A pair needs no numbers of its own: it runs from the lower step’s minimum to the upper step’s maximum. The original per-step clamp() definitions are kept as the floor for engines without progress(), the tan(atan2()) construction, or round().

One-up pairs

Each pair interpolates from the lower step’s minimum to the upper step’s maximum across the viewport range — used where a gap should sit between two steps rather than on one.

One honest exception: --space-30 is not actually fluid — it is a constant 5px at every width. Its multipliers produce 4.5px at the small end and 5px at the large end, and Utopia rounded both to 5.

Static spacing

The same ladder, frozen: identical percentage names, computed against a fixed 20px base — the fluid scale’s desktop anchor — and expressed in rem. The bars below measure exactly the same at phone and desktop widths; that is the point. From step 50 up, each value is identical to the fluid scale at desktop; the two smallest steps take the exact percentages (2px / 6px) instead of the fluid scale’s rounding artefacts.

Usage rule: fluid for layout-level spacing — page rhythm, section gaps, grid gutters, anything that should breathe with the viewport. Static for component-internal spacing — button and input padding, icon gaps, card interiors — where a component must measure the same wherever it is dropped, including contexts with no fluid root, such as exported Thoughts articles. There are deliberately no static pairs: a pair is a fluid transition between steps, and frozen it is just another static value — the ladder already covers the useful stops.

Layer 1 — Primitives

Radius

The 2023 Foundations values, renamed to the unified percentage convention with 0.5rem (8px) as base 100 — the same vocabulary as type, spacing and colour — and expressed in rem. Only --radius-full stays in px: 9999px is a sentinel, not a measurement.

The concentric rule: corners are concentric when their arcs share a centre, so outer radius = inner radius + gap. Equivalently, a nested element’s radius is governing radius − total inset — applied by the .u-concentric utility as border-radius: max(0rem, calc(var(--radius) - var(--inset))). Because the inset is usually a fluid spacing token, the calc rides the token and the corners stay concentric at every viewport width; an inset larger than the radius floors at 0 — square corners, never a negative radius.

Concentric demo

Three nested layers — panel, card, chip — under one governing radius, --radius-300 (1.5rem · 24px). Each layer is set on its own in the legend below the stage: with its Concentric switch on, a layer’s radius is its parent’s actual radius minus the gap — the panel, outermost, takes the governing radius itself; with the switch off, the layer takes the fixed radius picked in its select, whatever its parent does, and its children still derive from that actual radius. The readout computes each layer’s top-left corner-arc centre from its actual radius and its cumulative inset: a concentric layer shares its parent’s centre, a layer whose inset exceeds its parent’s radius floors to a square corner (which has no arc centre — its computed centre sits at its corner), and a fixed layer sets its own centre.

Layer 1 — Primitives

Motion

Animation was never captured in Figma — it wasn’t available there — so this primitive was defined in code first. Like every Layer 1 primitive the tokens are polysemic: they describe how things move, never why — there are no hover, error or success motions. Naming follows the unified percentage convention: 100 is the base value, here 200ms. Time has no relative unit, so values stay in ms — the same exception class as a 1px hairline.

Durations

Easings

Stagger

--stagger 50ms — the default interval between staggered items. In the explorer, an item’s delay is the selected interval × its index — the same rule as calc(var(--stagger) × its index) at the default.

Motion explorer

Five items, one combination

Combination:

The token displays above are the controls — pick a duration, an easing and a stagger and the stage re-runs the moment a selection changes, no replay needed. Duration and easing are read live from the page’s own tokens via getComputedStyle, so what moves is the token itself: under reduced motion the durations read as 0ms and every item lands instantly. The total is one duration plus four stagger intervals — the last item’s delay.

Under reduced motion the parallax layers do not translate and enlarge/zoom become instant — the durations collapse to 0ms at token level, and the parallax driver checks the same media query before moving anything.

The rules

  • Delays reuse the duration tokens. There is no separate delay scale — transition-delay and animation-delay take duration tokens, and --stagger is the default interval between staggered items.
  • Movement offsets use the spacing tokens. There is no distance scale either — an element travels by a spacing token (static inside components, fluid at layout level), so motion inherits the spacing rhythm instead of duplicating it.
  • Keyframes live in the components. These tokens control only the timing character — duration, curve, interval — everywhere; what actually moves is each component’s own business.
  • Reduced motion is a token-level contract. Under prefers-reduced-motion, every duration and the stagger collapse to 0ms, so every consumer becomes instant without per-component work. Components must also drop looping, parallax and large-travel animation under the same media query — the tokens cannot do that part for them.

Layer 1 — Primitives

Opacity

One global scale, defined once — opacities are not scoped per scheme. The colour schemes stay at eight slots and never override these values; interactive states are built by consuming steps from this scale directly. Naming follows the unified percentage convention: the number is the percentage of full opacity. Each swatch is the same ink — --midnight-1000 — laid at that step over a split light/dark backdrop, so what you see is the translucency itself. Click any swatch to copy its CSS variable.

How it’s consumed

Directly, as an opacity value — opacity: var(--opacity-40) fades whole content, which is how disabled states are built.

In color-mix, as a percentage — the scale is unitless, so it converts inline: color-mix(in oklch, var(--action-border) calc(var(--opacity-10) * 100%), transparent) tints any colour token without a new token.

The standard state mapping — guidance, not tokens; components reference the steps directly. Hover: a state layer of the component’s own ink colour at --opacity-10 over the resting surface. Active: the same layer at --opacity-15. Disabled: content at --opacity-40, and the states stop responding. Focus-visible is not opacity-led: a solid ring in --action-border with an offset — focus needs certainty, not a tint.
