Design System Specimen — Components

Components

The first real components, built as a test of the token architecture. Each one consumes the eight scheme slots and the global scales — never a colour family directly — so a single implementation re-skins under any scheme. Each is shown live in a stage you can re-scope across all seven families and both modes, and each ships with the contract it is built and tested against: a truth table (inputs → rendered output, don’t-cares compressed) and, where behaviour runs over time, its transitions. The first set: the selector button, the toggle switch, and the action buttons.

Component 01

Selector Button

A generic single-select control: it picks one value from a set of options and reports the pick. Its inputs are the options — each a label, an optional glyph, and a value — plus the selected value; its only output is a selection-change notification carrying the new value. It carries no business logic: it does not know what the options mean, and it does nothing with a selection beyond reporting it, so the same component serves any pick-one job. Collapsed, it is a single pill carrying the selected option; activated, it opens a panel below it. Inside the panel only the selected option keeps the filled pill; deselected options sit bare and take a pill-shaped highlight on hover — the pill bar’s pattern.

The Mode Switch in the top row is an application of this component: the shell supplies Light, System, and Dark as the options and wires the selection-change notification to the page’s data-mode — that wiring is the shell’s, not the component’s. The stage instance below is a second application, deliberately meaningless: its options are Alpha, Beta, and Gamma, and its notifications go only to the readout under the stage.

Implementation: .selector-btn — consumes --text-fg-1, --surface-bg, --surface-border, --action-border, --page-fill, plus the opacity and motion scales. Inputs: options + a selected value. Output: a selection-change notification.

Component 02

Toggle switch

A binary control (role="switch") built only from scheme slots plus the global opacity and motion scales. ON takes the Primary action’s fill; OFF is outlined like the Secondary action — transparent fill, --action-border outline and knob — so switch and buttons read as one family. The track’s border is 1px in both states (transparent when ON), so toggling never shifts layout.

Implementation: .toggle — consumes --action-bg-1, --action-fg-1, --action-border, plus the opacity and motion scales.

Geometry: track 2.75rem × 1.5rem; knob 1.125rem, borderless, sitting 3px from the track’s outer edge in both states — the knob rests 0.125rem inside the track’s padding box and the 1px border makes up the rest, so the 1.25rem ON travel lands it symmetric. Activation (click, Space, or Enter) flips aria-checked and the knob travels over --duration-100 / --ease-out; under reduced motion it snaps.

Invariant: --action-border = --action-bg-1 in all 14 schemes, so the OFF outline always matches the ON fill. The disabled row is the one the specimen’s scheme-card prototype never exercised — it is codified here first.

Component 03

Action buttons

The Primary / Secondary pair. Primary takes the scheme’s action fill; Secondary is its outline twin — transparent fill, --text-fg-1 label, 1px --action-border. States are not new colours: hover and active lay the button’s own ink over itself at the global --opacity-10 / --opacity-15, focus is a solid ring, and disabled drops the whole button to --opacity-40. One recipe covers both variants and both modes, with no per-scheme tuning.

Implementation: .state-btn with .state-btn-primary / .state-btn-secondary — consumes --action-bg-1, --action-fg-1, --action-border, plus the global opacity scale.
