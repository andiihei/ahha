Design System Specimen — Strategy

Making the system AI-ready

Draft — proposal, awaiting ratification. Saved 2026-10-21.

An AI-ready system is one where an agent can build a correct, on-system component without a human in the loop for taste — because everything it needs is machine-readable, the rules are explicit, and violations are caught by machines, not by your eyes.

  1. Tokens become data, not just CSS.

    The design-language CSS files stay the human layer, but a build script generates a machine-readable token file (W3C Design Tokens JSON) from them — never hand-maintained, so they can’t drift. The tokens live in the design system’s own repository and ship as a versioned package; projects consume the package by pinning a version and upgrade by deliberate bump. CI checks run in that repo and validate every brand pack against the contract: every scheme defines all 8 slots, across all 14 schemes in the pack; naming follows the grammar; the units rule is enforced (no stray px outside the sanctioned exceptions); no raw colour values outside colors.css; and contrast holds for every brand. This automates the diff checks that have been run by hand so far.

  2. Components become contracts.

    A component registry that lives with the package — one structured entry per Lit component: name, its Figma source (read-only reference), props/slots/events, exactly which tokens and slots it consumes, its state recipe (the opacity/state-layer mapping), accessibility notes, and one canonical usage example. Components are brand-agnostic: they consume the scheme slots, never a brand directly, so one registry serves every brand pack. The seed set is the preview-card cluster: Primary/Secondary actions, the Toggle, cards, accordion, header/footer. An AI doesn’t guess how a toggle works; it reads the contract.

  3. Rules become a context pack.

    One canonical brief an agent loads before touching anything — encoding the judgments, not just the values: polysemy (no purpose semantics), the scope rule (Haze default, Midnight brand, nothing colourised unscoped), global-only opacity, the motion + reduced-motion contract, the units rule, and the Figma read-only rule. Plus an llms.txt-style index over the token files, registry, and specimen, so any agent can find the right layer fast.

  4. Access becomes tooling, with a review surface.

    EmDash’s built-in MCP for content work under its permissions; Figma stays read-only for audits; version control is trunk-based — one trunk (main) in GitHub, Cloudflare deploying from trunk, trunk always deployable. Work lands in small, frequent integrations directly to trunk by default; any branch is single-purpose and lives under a day or two; there are no develop or release branches, and releases are tags on trunk. Incomplete work lands dark — unlinked routes, draft content, flags — rather than waiting on a branch. CI is the gate: the pillar-1 checks and the build run on every trunk commit, and trunk is protected by required CI only, with no required PR reviews. Review happens post-merge, on the deployed preview, and a revert is the cheap undo. A short PR is the exception, kept for token-contract changes and EmDash schema/seed changes only. The inspector’s copied reports are the debug currency when something is off.

  5. Proof, not vibes: golden examples + evals.

    The specimen — the system’s own documentation site — supplies the golden renders. On top, a small eval suite: fixed prompts (“build a Showcase card in Fern Dark”, “add a form field with an error state”) scored automatically against the rules — correct slots, no invented tokens, no unscoped colour, states per recipe. The suite runs against every brand pack, not just one brand. The system graduates when a fresh agent passes the suite cold.

Graduation gate

  • Tokens-as-data with CI green
  • Registry covering the seed components
  • Context pack written and loading cleanly
  • MCP + trunk-based workflow live
  • Eval suite passing

The checklist that ends the specimen phase and starts the build phase.

The two failure modes this defends against: an AI inventing tokens or colours (caught by pillars 1 + 5), and silent drift between CSS, token data, and specimen (caught by generation + diffs, never by memory).
